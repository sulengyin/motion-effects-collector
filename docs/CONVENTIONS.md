# 约定 · CONVENTIONS

> 2026-11-04 定稿。这份文件管"怎么做"，`SCHEMA.md` 管"字段怎么填"，`PROGRESS.md` 管"做过什么"。
> 改约定必须单独提一个 `docs:` 提交，并在文末变更记录里留一行。

## 一、分支

主干开发，不设 `dev`。`main` 永远处于可交付状态：双击 `index.html` 能用，`dist/` 是最新构建。

| 场景 | 做法 |
|---|---|
| 文案、调参、单条修复 | 直接提交 `main` |
| 一批新效果（≥3 条） | 开 `feat/<批次-slug>`，做完 squash 合回 `main` |
| 修现象类 bug | 开 `fix/<现象-slug>` |
| 纯文档 / 结构调整 | `docs/<主题>` |

- 分支名全小写，连字符分隔，例：`feat/b4-material-3d`、`fix/auto-scroll-jump`。
- 合并方式：`git merge --squash` → 一个提交 → 删分支。保留批次边界，不制造无意义的合并节点。
- 禁止：force push `main`、amend 已推送提交、留超过一周的分支、在 `main` 上直接 rebase 已公开历史。

理由：单人项目开 PR 评审是纯开销，但批次隔离能让"这批出问题"只回滚一个提交，而不是在 `main` 上逐个挑。

## 二、提交

沿用 Conventional Commits，type 只用四个：

| type | 用途 |
|---|---|
| `feat` | 新增效果、新增页面能力 |
| `fix` | 修 bug、修显示错误 |
| `docs` | 文档、词表、计划 |
| `chore` | 构建脚本、配置、清理 |

- 标题：`type: 做了什么（数量变化）`，≤50 字。例：`feat: B3 滚动 5 条入库（37 → 42），新增滚动分类`
- 正文三段，缺一不可：**改了什么 / 为什么这么改 / 验证了什么**。
- 标题禁止：`update`、`修改`、`优化`、`提交`——没有信息量的标题等于没写。
- 一个提交只讲一件事。加效果和改页面外壳不混；随批次同步的文档可以同提交，但正文要写明。
- 决策记录进 `docs/PROGRESS.md`，不要只留在提交正文或对话里。

**`feat` 硬门槛**（缺一项不算完成）：

1. `node tools/check.js` 通过，且 `dist/` 已重建；
2. `docs/GLOSSARY.md` 加了对应词条；
3. README 的效果数与分类表同步；
4. 新效果的 `note` 里写了至少一个真实的坑，而不是复述定义。

## 三、仓库结构

```
index.html     页面外壳，唯一入口
effects.js     唯一数据源，所有效果都在这
dist/          构建产物，不手改
tools/         构建与校验脚本
docs/          契约 / 词表 / 计划 / 进度 / 本文件
inbox/         投喂原料，gitignore 排除
```

- 效果只能进 `effects.js`。`index.html` 里不许出现具体效果名或只服务某条效果的样式，否则加一条要改两处，迟早漏。
- `dist/` 由 `tools/build-standalone.js` 生成，提交前必跑，不许直接编辑产物。
- `docs/` 五份各管一件事，不合并、不互相抄。
- 不引入 `package.json`、构建工具、CDN、外部字体、图片资源。"断网双击可用"是硬约束，不是偏好。
- 拆分阈值：`effects.js` 超过 80 条或 4000 行，才考虑拆成目录。现在不拆。

## 四、敏感信息

不提交清单：

- 任何 token、私钥、`.env`、账号密码、Cookie；
- 客户/公司的真实业务截图、后台界面、品牌 logo；
- 付费字体、付费模型、有版权的视频素材；
- 排错过程中打印出的账号信息、内网地址。

具体规则：

- `inbox/` 已在 `.gitignore` 里，但普通忽略拦不住 `git add -f`。加文件前先看体积和内容。
- 提交身份统一用 GitHub noreply：`347252934+sulengyin@users.noreply.github.com`（仓库级 `user.email` 已设置）。历史提交保持原样，不重写。
- 泄露处置顺序：撤销凭据 → 清理文件 → 必要时改历史并 force push → 在 `PROGRESS.md` 记一条。改历史属于破坏性操作，先确认。

## 五、协作

当前只有作者和 AI 助手，不铺多人流程，但保留可交接性。

**助手每次推送前的固定动作**：`node tools/check.js` → 重建 `dist` → 同步计数 → 提交 → push → 用 API 核对远程 SHA。任一步失败就不推，如实说明卡在哪。

**必须事先确认的破坏性操作**：force push、改写历史、删除分支、更换 LICENSE、改仓库可见性、大规模重命名 id。

**投喂流程**（详见 `SOURCES.md`）：一句话/截图/视频 → 判定是新效果还是变体 → 中英命名 → 拆参数 → 写实现 → 归档 → 更新词表与进度。同一动作不同参数、不同触发，只记 `variants`，不新建条目。

**交接**：新接手的人只需读三份——`README.md`（怎么用）、本文件（怎么做）、`SCHEMA.md`（怎么加）。
